# pLedger 外部写入兼容规范

本文档定义外部程序如何向思源笔记写入 pLedger 数据，使数据能够被 pLedger 正确发现、解析、展示、统计和继续编辑。

本文档适用于绕过 pLedger 界面、通过思源 CLI、API、MCP、Agent、Skill、脚本或其他受支持方式写入数据的实现。

## 1. 文档定位

本文档是 pLedger 的外部写入兼容协议，不是 Agent 的图片识别指南，也不是特定工具的调用教程。

本文档规定：

- 如何解析 pLedger 配置；
- 块正文、Markdown 表格和块属性使用什么格式；
- 数据字段之间必须满足哪些一致性约束；
- 写入、验证和失败回滚应遵循什么顺序。

本文档不规定：

- 如何进行 OCR 或图片识别；
- 如何从商户名称推断分类；
- Agent 何时以及如何向用户提问；
- 使用哪个模型、MCP、CLI 或提示词；
- 多币种换算和第三方订单状态验证。

外部程序可以自行实现上述能力，但最终写入思源的数据必须符合本规范。

### 1.1 工具无关原则

本规范只约束写入后的思源数据状态，不绑定具体调用工具、命令名称、接口路径或传输协议。

文档中的“读取”“查找”“创建”“插入”“更新”“删除”“设置”和“查询”等表述，表示实现必须完成的思源数据操作。实现可以使用当前环境支持的 CLI、API、MCP、SDK 或其他方式完成这些操作。

判断是否符合本规范时，只检查最终的数据位置、内容、属性和一致性，不检查实现采用了哪一种调用方式。

## 2. 规范用语

本文档使用以下约束级别：

- **必须**：不满足时，数据可能无法被 pLedger 识别，或者会被数据维护功能判定为异常；
- **应当**：强烈建议遵守，用于避免重复数据、部分写入或覆盖已有数据；
- **可以**：不影响兼容性的可选行为。

## 3. 兼容性目标

符合本规范的数据应满足以下目标：

1. pLedger 能够在正确的数据范围内发现记录；
2. pLedger 能够解析记录中的日期、分类和金额；
3. 记录能够参与列表展示和统计计算；
4. 记录能够继续通过 pLedger 界面编辑；
5. 记账记录不会被数据维护功能判定为字段缺失或位置冲突；
6. 外部写入失败时，不会遗留只有正文或只有部分属性的半成品数据。

## 4. 两种数据模型

pLedger 包含“资产”和“记账”两个模块。两者的数据含义和存储格式不同，外部程序不得混用。

| 模块 | 数据含义        | 思源存储形式             | 识别与保护机制                 |
| -- | ----------- | ------------------ | ----------------------- |
| 资产 | 指定日期的资产余额快照 | 年度文档中的 Markdown 表格 | 保存后锁定年度文档               |
| 记账 | 一笔收入或支出     | 单独的 Markdown 块     | 通过 `custom-pledge` 识别记录 |

资产记录不是交易流水；记账记录也不是账户余额快照。

## 5. 配置发现

### 5.1 配置文件位置

pLedger 的插件名称是 `siyuan-pledger`，配置文件名是 `setting.json`。在思源工作空间中的标准位置为：

```text
/data/storage/petal/siyuan-pledger/setting.json
```

不同调用工具可能使用不带开头 `/` 的工作空间相对路径：

```text
data/storage/petal/siyuan-pledger/setting.json
```

外部写入程序必须在每次写入前读取当前配置，不建议把配置内容永久硬编码在实现中。

外部写入程序不得直接修改 `setting.json`。配置变更应由用户通过 pLedger 设置界面完成。

### 5.2 配置字段

与外部写入有关的字段如下：

| 字段                       | 模块 | 类型     | 说明                         |
| ------------------------ | -- | ------ | -------------------------- |
| `documentId`             | 资产 | string | 资产数据根文档 ID                 |
| `config`                 | 资产 | string | 字符串形式的资产分类 JSON            |
| `bookkeepingDocumentId`  | 记账 | string | 集中存放时为根文档 ID；按日期存放时为笔记本 ID |
| `bookkeepingStorageMode` | 记账 | string | `central` 或 `date`         |
| `bookkeepingConfig`      | 记账 | string | 字符串形式的记账分类 JSON            |

以下字段不参与记录定位和数据格式：

- `planNum`：资产目标金额；
- `bookkeepingMonthlyBudget`：每月预算；
- `iconConfig`：自定义展示图标。

### 5.3 分类配置解析

`config` 和 `bookkeepingConfig` 都是字符串形式的 JSON，需要在读取 `setting.json` 后再次解析。

```js
const setting = JSON.parse(settingFileContent);
const assetConfig = JSON.parse(setting.config);
const bookkeepingConfig = JSON.parse(setting.bookkeepingConfig);
```

分类配置示例：

```json
[
  {
    "name": "现金资产",
    "icon": "💵",
    "children": [
      { "name": "现金" },
      { "name": "银行卡" }
    ]
  }
]
```

当前 pLedger 只支持两级分类。分类配置必须满足：

- 最外层是非空数组；
- 每个一级分类具有非空的字符串 `name`；
- 一级分类名称不重复；
- 每个一级分类具有非空的 `children` 数组；
- 每个二级分类具有非空的字符串 `name`；
- 同一个一级分类下的二级分类名称不重复；
- 二级分类不得继续包含 `children`；
- `icon` 只用于界面展示，不写入资产或记账业务数据。

配置不存在、为空或无法解析时，外部程序必须停止对应模块的写入。

### 5.4 分类名称约束

写入数据使用的一级和二级分类名称必须与当前配置完全一致，包括大小写和空格。

外部程序不得：

- 擅自创建配置中不存在的分类；
- 使用近义词替换配置名称；
- 把二级分类挂到错误的一级分类下；
- 将 `icon` 作为分类名称写入数据。

## 6. 记账写入规范

### 6.1 确定记账目标文档

目标文档由 `bookkeepingStorageMode` 决定。

#### 6.1.1 集中存放

当 `bookkeepingStorageMode` 为 `central` 时：

- `bookkeepingDocumentId` 必须是可访问的根文档 ID，在配置文件中取出；
- 目标月份取自记录的 `date`，格式为 `YYYY-MM`；
- 记录必须写入根文档下标题为 `YYYY-MM` 的月份子文档；
- 查找月份子文档时，应兼容文件名 `YYYY-MM` 和 `YYYY-MM.sy`；
- 月份子文档不存在时，可以在根文档下创建。

例如：

```text
date: 2026-08-12
目标月份文档标题: 2026-08
```

#### 6.1.2 按日期存放

当 `bookkeepingStorageMode` 为 `date` 时：

- `bookkeepingDocumentId` 必须是可访问的笔记本 ID，由配置文件取出；
- 必须读取该笔记本配置；
- 必须使用 `conf.dailyNoteSavePath` 生成记录日期对应的日记路径；
- 应根据生成的路径查找已有日记；
- 日记不存在时，可以按该路径创建；
- 记录必须写入该日期对应的日记文档。

pLedger 当前保存逻辑支持日记路径中的以下 Go 日期布局标记：

| 标记     | 含义    |
| ------ | ----- |
| `2006` | 四位年份  |
| `01`   | 两位月份  |
| `1`    | 不补零月份 |
| `02`   | 两位日期  |
| `2`    | 不补零日期 |
| `15`   | 两位小时  |
| `04`   | 两位分钟  |
| `05`   | 两位秒   |

如果路径渲染后仍包含未解析的 `{{ ... }}` 表达式，外部程序必须停止写入。

### 6.2 记账块正文

每条记账记录对应一个独立的 Markdown 块。块正文格式为：

```text
日期|一级分类|二级分类|收支中文名称|两位小数金额|备注
```

示例：

```text
2026-08-12|餐饮|午餐|支出|28.50|某面馆
```

正文生成规则：

- `expense` 在正文中写为 `支出`；
- `income` 在正文中写为 `收入`；
- 金额固定保留两位小数；
- 字段使用半角竖线 `|` 分隔；
- 正文首尾不添加额外的 `|`。

每个字段必须按以下顺序进行 Markdown 表格单元格转义：

1. `\` 转换为 `\\`；
2. `|` 转换为 `\|`；
3. 换行转换为文本 `\n`。

### 6.3 创建记账块

目标文档确定后，必须在该文档中插入一个 Markdown 块，并将第 6.2 节生成的文本作为块内容。

该操作必须满足：

| 项目   | 要求             |
| ---- | -------------- |
| 目标位置 | 第 6.1 节确定的目标文档 |
| 块类型  | Markdown 块     |
| 块内容  | 第 6.2 节生成的完整正文 |
| 操作结果 | 能够取得实际创建的块 ID  |

外部程序必须取得思源实际创建的块 ID。未取得有效块 ID 时，不得继续写入属性。

### 6.4 `custom-pledge` 属性

记账块必须具有名为 `custom-pledge` 的自定义属性。该属性的值是完整记录对象序列化后的 JSON 字符串。

完整记录示例：

```json
{
  "type": "expense",
  "date": "2026-08-12",
  "parentName": "餐饮",
  "childName": "午餐",
  "amount": 28.5,
  "remark": "某面馆",
  "month": "2026-08",
  "storageMode": "central",
  "storageRootId": "20260801090000-rootdoc",
  "documentId": "20260801120000-monthdoc",
  "blockId": "20260812123000-recordid",
  "createdAt": "2026-08-12T04:30:00.000Z",
  "displayTime": "12:30"
}
```

属性字段约束：

| 字段              | 必填 | 类型     | 约束                        |
| --------------- | -: | ------ | ------------------------- |
| `type`          |  是 | string | 只能是 `income` 或 `expense`  |
| `date`          |  是 | string | 格式为 `YYYY-MM-DD`，且必须是真实日期 |
| `parentName`    |  是 | string | 当前记账配置中的一级分类              |
| `childName`     |  是 | string | `parentName` 下的二级分类       |
| `amount`        |  是 | number | 大于 0 的有限数字，不能是数字字符串       |
| `remark`        |  是 | string | 允许为空字符串                   |
| `month`         |  是 | string | 必须等于 `date.slice(0, 7)`   |
| `storageMode`   |  是 | string | `central` 或 `date`        |
| `storageRootId` |  是 | string | 数据所属配置的根文档 ID 或笔记本 ID     |
| `documentId`    |  是 | string | 记录块实际所属文档 ID              |
| `blockId`       |  是 | string | 承载该属性的实际块 ID              |
| `createdAt`     |  否 | string | ISO 日期时间字符串               |
| `displayTime`   |  否 | string | `HH:mm` 格式的本地显示时间         |

`custom-pledge` 只能包含上表定义的字段。`id`、`icon` 等非标准字段不得写入。

### 6.5 写入记账属性

必须为实际记录块设置以下属性：

| 项目  | 要求                          |
| --- | --------------------------- |
| 目标  | 实际创建的记录块                    |
| 属性名 | `custom-pledge`             |
| 属性值 | 第 6.4 节完整记录对象序列化后的 JSON 字符串 |

注意：

- `custom-pledge` 的外层属性值必须是字符串；
- 字符串内部的 `amount` 必须仍然是 JSON 数字；
- `blockId` 和 `documentId` 必须来自实际写入结果，不能预先伪造；
- 正文中的日期、分类、类型、金额和备注必须与属性中的对应字段一致。

### 6.6 记账一致性约束

一条有效记录必须同时满足：

```text
custom-pledge.blockId = 承载属性的实际块 ID
custom-pledge.documentId = 块实际所属文档 ID
custom-pledge.month = custom-pledge.date 的 YYYY-MM 部分
custom-pledge.storageMode = 写入时使用的存放方式
custom-pledge.storageRootId = 写入时读取的 bookkeepingDocumentId
custom-pledge.parentName = 当前配置中的一级分类
custom-pledge.childName = 该一级分类下的二级分类
```

对于 `central` 模式，实际文档必须位于配置根文档范围内。

对于 `date` 模式，实际文档必须位于配置指定的笔记本内。

### 6.7 记账写入顺序

外部程序必须按以下顺序创建记录：

1. 读取当前配置；
2. 校验待写入字段和分类；
3. 确定或创建目标文档；
4. 生成块正文；
5. 插入 Markdown 块；
6. 取得真实 `blockId`；
7. 取得块实际所属的 `documentId`；
8. 生成完整属性；
9. 写入 `custom-pledge`；
10. 重新查询并验证记录。

### 6.8 记账失败回滚

如果块创建成功，但属性写入失败，外部程序必须：

1. 删除刚创建的块；
2. 验证该块已经删除；
3. 报告本次写入失败。

不得遗留没有 `custom-pledge` 属性的半成品记账块。

如果删除也失败，外部程序必须报告实际块 ID，并停止自动重试。

### 6.9 记账写入后验证

至少检查：

- 块存在于预期文档；
- `custom-pledge` 属性存在；
- 属性值能够解析为 JSON 对象；
- 所有必填字段存在且类型正确；
- ID、日期、月份、存放方式和实际位置一致；
- 分类存在于当前配置；
- 金额是大于 0 的数字。

验证方式由所用工具决定，但验证结果必须来自写入后的实际思源数据，不能只检查本地待写入对象。

## 7. 资产写入规范

### 7.1 资产年度文档

资产根文档由 `setting.documentId` 指定。

外部程序必须：

1. 从资产日期提取四位年份；
2. 在资产根文档下查找同名的年度子文档；
3. 查找时兼容文件名 `YYYY` 和 `YYYY.sy`；
4. 年度文档不存在时，可以在资产根文档下创建；
5. 将该年份的资产记录写入对应年度文档。

例如：

```text
date: 2026-08-12
年度文档标题: 2026
```

### 7.2 资产表格块

pLedger 读取年度文档中的第一个表格块作为资产数据源。外部程序不得在同一年度文档中另建第二个资产表格来追加数据。

如果年度文档中已有表格块，必须更新该表格块。

如果不存在表格块，可以创建新的 Markdown 表格块。

### 7.3 资产表头

当前 pLedger 支持两级资产分类，对应表头为：

```markdown
| 日期 | 类型1 | 类型2 | 金额 |
| --------- | --------- | --------- | --------- |
```

列顺序必须保持为：

1. 日期；
2. 一级分类；
3. 二级分类；
4. 金额。

外部程序不得增删列或调整列顺序。

### 7.4 资产数据行

每个二级分类对应一行：

```markdown
| 2026-08-12 | 现金资产 | 现金 | 500.00 |
| 2026-08-12 | 现金资产 | 银行卡 | 12000.00 |
```

生成规则：

- 日期使用 `YYYY-MM-DD`；
- 分类名称必须与配置完全一致；
- 金额固定保留两位小数；
- 每行列数必须与表头一致；
- 表格单元格使用第 6.2 节定义的相同转义规则。

各列写入约束：

| 列   | 格式                       |
| --- | ------------------------ |
| 日期  | `YYYY-MM-DD`，且必须是真实日期    |
| 类型1 | 当前资产配置中的一级分类             |
| 类型2 | `类型1` 下的二级分类             |
| 金额  | 有限数字格式化为两位小数，可以为 `0` 或负数 |

完整示例：

```markdown
| 日期 | 类型1 | 类型2 | 金额 |
| --------- | --------- | --------- | --------- |
| 2026-08-12 | 现金资产 | 现金 | 500.00 |
| 2026-08-12 | 现金资产 | 银行卡 | 12000.00 |
| 2026-08-12 | 投资资产 | 股票 | 25000.00 |
| 2026-08-12 | 投资资产 | 基金 | 8000.00 |
```

### 7.5 新增资产记录

新增资产快照时，外部程序应当：

1. 读取当前资产配置；
2. 校验日期、分类和金额；
3. 查找或创建年度文档；
4. 查找年度文档中的第一个表格块；
5. 表格不存在时生成标准表头；
6. 生成资产数据行；
7. 将新行追加到现有表格末尾；
8. 更新已有表格块，或者创建第一个表格块；
9. 锁定年度文档；
10. 重新读取并验证表格。

更新时必须替换已有表格块的 Markdown 内容。创建时必须在年度文档中插入第一个 Markdown 表格块。具体命令或接口形式由所用工具决定。

### 7.6 修改已有资产记录

pLedger 当前编辑逻辑以“日期 + 一级分类”定位一组资产行。

修改某一一级分类时，外部程序必须：

1. 读取年度文档中的最新表格内容；
2. 保留表头和其他已有数据行；
3. 找到日期与目标日期相同、一级分类与目标分类相同的所有行；
4. 删除这组旧行；
5. 在原位置写入该一级分类重新生成的二级分类行；
6. 更新整个表格块；
7. 再次锁定年度文档；
8. 重新读取并验证结果。

如果找不到待修改的原记录，不得静默改为新增，否则可能产生重复快照。

### 7.7 锁定资产年度文档

资产表格保存成功后，建议通过思源支持的文档锁定方式锁定年度文档。

锁定用于降低用户直接编辑资产表格造成数据损坏的风险，不是必须的操作。

### 7.8 资产并发与覆盖保护

资产写入会更新整个 Markdown 表格块，因此外部程序应当：

- 在生成新表格前读取最新的表格内容；
- 不使用长期缓存的表格内容覆盖当前数据；
- 更新后重新读取表格；
- 验证更新前已有的其他日期和分类仍然存在；
- 发现表格在读取和写入之间发生变化时，重新读取并重新生成更新内容。

### 7.9 资产失败处理

如果表格更新失败，外部程序必须重新读取表格确认实际状态，不得在状态不明时重复追加。

如果表格保存成功但年度文档锁定失败：

1. 资产数据可能已经成功写入；
2. 必须查询确认目标行是否存在；
3. 不得再次追加同一批数据；
4. 应报告年度文档 ID 和锁定失败状态。

### 7.10 资产写入后验证

至少检查：

- 年度文档存在且年份正确；
- 年度文档中的第一个表格块存在；
- 表头和列顺序正确；
- 每个目标数据行均可解析；
- 日期、分类和金额与待写入数据一致；
- 更新前已有的非目标数据仍然存在。

***

## 8. 写入重试约束

### 8.1 记账

写入实现应保存新建块的真实 ID。重试前应先查询该 ID：

- 块和合法属性都存在：视为已经成功，不再创建；
- 块存在但属性不存在：先回滚或修复半成品；
- 块不存在：可以重新执行写入。

### 8.2 资产

资产写入会更新整个表格块。写入结果未知时，必须重新读取目标表格并核对目标行，不得直接重复提交相同的表格更新。

## 9. 禁止行为

外部写入程序不得：

- 修改 pLedger 的 `setting.json`；
- 使用配置中不存在的分类；
- 混用记账和资产的存储结构；
- 给资产数据写入 `custom-pledge`；
- 把记账数据追加到资产表格；
- 只写记账正文而不写 `custom-pledge`；
- 使用预先生成的假 `blockId` 或 `documentId`；
- 只修改记账正文而不更新对应属性；
- 在写入状态不明时盲目重试；
- 使用旧的资产表格缓存覆盖最新表格；
- 在标准字段之外写入未定义字段。
